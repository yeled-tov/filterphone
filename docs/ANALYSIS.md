## 2. איך זה בנוי — המסלול של תמונה

```
טלפון ──WireGuard──▶ wg0 (10.8.0.1)
                       │
         DNS ──────────┼──▶ AdGuard Home (חסימת דומיינים)
                       │
   TCP 80/443 ─────────┼──▶ iptables REDIRECT ──▶ mitmproxy :8080 (transparent)
                       │        │  מנפיק תעודה מזויפת לכל אתר, חתומה ב-CA של השרת
                       │        │  (הטלפון חייב לסמוך על ה-CA הזה)
                       │        ▼
                       │   response hook: אם content-type=image/* וגודל 1.5KB–10MB:
                       │     1. רמת סינון ← Redis לפי ה-IP של הלקוח ב-VPN (ברירת מחדל 3)
                       │     2. NudeNet (חלקי גוף) → YOLOv8-pose (שלד/מגדר) → אחוז עור
                       │     3. decide_action → חסימה (403 ריק) / צביעה בשחור / מעבר
   UDP 443 (QUIC) ─────┴──▶ REJECT — מכריח את הדפדפן לחזור ל-TCP כדי שה-MITM יראה
```

**רמות סינון:** 1 = קשוח (כל אישה נחסמת), 2 = צביעת עור בשחור, 3 = רק עירום מפורש.

**לא נבדקים** (`--ignore-hosts`): googleapis, googleusercontent, youtube, googlevideo, ytimg, mail/chat google, claude.ai, truecaller, termius.

## 3. מהירות — מדידות

### הצנרת הנוכחית (12 תמונות אמיתיות, 800×600)

| שלב | חציון | מקסימום |
|---|---|---|
| NudeNet | 89ms | 110ms |
| YOLOv8-pose | 125ms | 185ms |
| זיהוי עור | 5ms | 6ms |
| **סה"כ לתמונה** | **225ms** | 280ms |

### למה זה מרגיש איטי הרבה יותר מ-225ms

1. **כל הסינון רץ בתוך לולאת האירועים היחידה של mitmproxy.** ה-hook מוגדר כפונקציה רגילה ולא אסינכרונית, ולכן בזמן שתמונה נבדקת **כל התעבורה של כל המשתמשים נעצרת**, גם בקשות שאינן תמונות. בדף עם 30 תמונות נוצר תור של כ-7 שניות.
2. **ה-Cache כבוי** (`USE_CACHE = False` ב-`cache_manager.py`). אותו לוגו נבדק מחדש בכל פעם.
3. NudeNet כותב כל תמונה **לקובץ זמני בדיסק** (וזו גם הסיבה שהסינון נשבר כשהדיסק התמלא).
4. כל תמונה מפוענחת 3 פעמים: PIL, OpenCV ו-NudeNet.

### 🟡 מגבלה מהותית של סינון בצד השרת (חשוב לתכנון האפליקציה)

- **אנדרואיד 7 ומעלה:** אפליקציות **לא סומכות** על תעודות CA שהמשתמש התקין. הסינון דרך ה-MITM עובד ב-**Chrome** (ובעוד כמה דפדפנים). שאר האפליקציות שמנסים ליירט אותן נכשלות ב-TLS, ו-mitmproxy כרגע לא מעביר אותן אוטומטית הלאה, כך שהן פשוט נשברות. צריך מנגנון **passthrough אוטומטי**: חיבור שנכשל ב-TLS עובר בפעם הבאה בלי יירוט.
- **אייפון:** אחרי התקנת פרופיל והפעלת "אמון מלא" (Full Trust), רוב האפליקציות וגם Safari סומכים על ה-CA. היוצאות מהכלל הן אפליקציות עם Certificate Pinning (וואטסאפ, בנקים, חלק מהרשתות החברתיות).
- להשוואה, "מושגח" הוא **דפדפן**, ולכן גם הוא מסנן רק בתוך הדפדפן שלו.

## 5. הצעת האצה — שיטת "מושגח" מותאמת לשרת

### מדידת מודלים על המעבד של השרת

| מודל | תמונה בודדת | באצ' של 8 (לתמונה) |
|---|---|---|
| הצנרת הנוכחית (NudeNet + YOLO + עור) | 225ms | — |
| SigLIP-base, int8 | 238ms | 179ms |
| SigLIP-base, fp32 | 582ms | 451ms |
| MobileCLIP-S0, fp32 | 182ms | **124ms** |
| MobileCLIP-S1, fp32 | 334ms | 236ms |

> בזמן המדידה המעבד היה עמוס חלקית (rsyslog ו-VNC), כך שבשרת נקי המספרים צפויים להיות טובים יותר.

### המסקנה הכנה

**SigLIP עצמו לא יאיץ את השרת.** על מעבד ARM בלי מאיץ הוא איטי כמו הצנרת הנוכחית, או יותר. "מושגח" מהיר כי הוא רץ על ה-NPU של הטלפון. **ההאצה האמיתית באה מהארכיטקטורה:**

1. **מעבר אחד, הרבה החלטות.** מריצים מודל embedding אחד במקום שני מודלים והיוריסטיקות. מעליו יושבים **ראשי סיווג לינאריים** (אישה / עירום / בגד ים / לבוש לא צנוע / ...). כל ראש הוא מכפלה של 512–768 מספרים, כמה מיקרו-שניות. הוספת קטגוריה חדשה לא עולה כלום בזמן ריצה.
2. **Cache לפי hash.**
   - SHA-256 של הבייטים, נשמר ב-Redis. **שומרים ציונים גולמיים ולא החלטות**, כך שרשומה אחת משרתת את כל הרמות. גרסת המודל היא חלק מהמפתח.
   - שכבה שנייה לפי URL + ETag.
   - צפי: אחוז גבוה של פגיעות בגלישה רגילה (לוגואים, תמונות ממוזערות, CDN), עם תשובה בכ-1ms.
3. **בלי חסימת תעבורה.** ה-addon של mitmproxy הופך לאסינכרוני ושולח את התמונה ל**שירות inference נפרד** (Unix socket) עם micro-batching. אין יותר הקפאה גלובלית, ושאר התעבורה זורמת.
4. **Fail-closed לפי רמה.** ברמה 1, שגיאה היא חסימה ולא מעבר.
5. **בחירת מודל:** **MobileCLIP-S0 כשכבה ראשונה** (מהיר), ו-**SigLIP2 רק לתמונות שהתוצאה עליהן לא ודאית** (בערך 10–20%). מקבלים את הדיוק של SigLIP בעלות של MobileCLIP.
6. **אתחול הראשים בלי דאטה מתויג.** בהתחלה ה-zero-shot נעשה מ-embeddings של טקסט ("a photo of a woman", "nudity", "swimsuit"…). אחר כך מכיילים עם רגרסיה לוגיסטית על תמונות מהלוגים, עם תיוג ידני בממשק הניהול.

**צפי:** פגיעה ב-cache כ-1ms. בלי cache כ-120–180ms, **בלי לעכב שום תעבורה אחרת**. היום כל תמונה עולה 225ms ומקפיאה את כל השאר.
